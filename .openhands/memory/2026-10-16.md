## Skills layer + Alexa integration
Built a skills subsystem so capability is admin-switchable, modeled on
`personalities.py`. Key design point: gating is **bidirectional** — a disabled
skill removes both its prompt text *and* its tools from the model's tool list
(`skills.withheld_tool_names()` → `agent.usable_tools(cfg)`). Tools claimed by no
skill stay offered, so the old behaviour is the all-enabled default.

A skill may set `provider_field`; if the referenced config field is empty the
skill is dormant. The `alexa` skill uses `alexa_provider`, so five Alexa tools
never appear on an unconfigured box.

Research: **Amazon has no official API to command an Echo or make Alexa speak.**
Everything needs a bridge. Implemented three with deliberately unequal reach, and
each tool refuses with a specific explanation instead of silently no-op'ing:
- Voice Monkey — hosted HTTP, announce + routines only.
- alexacli (`github.com/buddyh/alexa-cli`) — the only route to a live voice
  command and to reading her reply back. Refresh token ~2 weeks.
- Home Assistant Alexa Media Player — announce only, but the most stable.

Verified the subprocess path with a stand-in `alexacli` on PATH, asserting the
exact argv (`speak "<text>" -d <device> --json`, etc.), plus the failure path
(auth expiry surfaces the CLI's own stderr message as a ToolError).

## alexacli: my first integration was wrong in four ways
My earlier "verified" test used a stand-in I wrote myself, which proved the
subprocess plumbing worked but NOT that my argv matched the real CLI. Reading
github.com/buddyh/alexa-cli (Go, MIT, 45 stars) properly found real bugs:

1. `-d <device>` is REQUIRED for speak/command/ask. `command.go` and `ask.go`
   both `MarkFlagRequired("device")`; `speak.go` errors "device is required (use
   -d or --announce)". My code omitted `-d` when no device was passed, so those
   calls would always have failed. Added `tools.alexacli_device` + `_device()`.
2. Output is wrapped: `Success` -> `{"success","message"}`, `Data`/`Devices` ->
   `{"success","data"}`. My code returned the envelope raw, so `alexa_devices`
   produced a dict instead of a list and `alexa_ask` never surfaced the answer.
   `_run_cli` now unwraps, and raises on `success: false`.
3. `list` as a parameter name shadowed the builtin, so `isinstance(data, list)`
   raised TypeError. Renamed to `list_routines`.
4. `go install .../cmd/alexa@latest` yields a binary named `alexa`, but every
   path in the tool calls `alexacli`. Correct install is
   `brew install buddyh/tap/alexacli` (Makefile BINARY_NAME=alexacli).

Also: `--announce` broadcasts to all Echoes (added as `announce: true`), and
`routine list/run` are documented WIP upstream -- the tool description says so.

## "Can't scroll the control room" -- the real cause
`style.css` sets `html, body { overflow: hidden }` because the chat HUD scrolls
its own inner panes. `admin.html` loads style.css *and* admin.css, so the admin
page inherited the lock: 4033px of content that could not be moved.

The trap: **`overflow: hidden` still permits scripted scrolling.** `scrollTo()`
worked, so earlier Playwright checks passed while a real user was stuck. Only
`page.mouse.wheel()` + keyboard reproduced it. Any future scroll check must use
wheel/keys, never `window.scrollTo`.

Fix: `admin.css` now sets `html { height: auto; overflow-y: auto }` and
`.admin-body { overflow: visible }`. admin.css is loaded only by admin.html, so
the chat page keeps its lock. Verify isolation when touching these rules.

## Responsive audit (the honest answer to "is it fully responsive?")
It was NOT. Fixing the scroll lock also *revealed* horizontal overflow that
`overflow: hidden` had been silently clipping. Four genuine bugs, all in
admin.css, all now fixed:

1. `.panel-head` was flex with no wrap and `.panel-actions { flex:none }`
   -> 214px horizontal overflow at 320px. Added `flex-wrap: wrap`.
2. `.kv-row strong` had no wrap rule. A long path (`/workspace/project/1e98b...`)
   set a min-content floor the flex row could not shrink below -> 144px overflow.
   Fixed with `min-width: 0` + `overflow-wrap: anywhere`.
3. `@media (max-width: 900px) { .persona-layout { grid-template-columns: 1fr } }`
   -- bare `1fr` is `minmax(auto, 1fr)`, and `auto` floors the track at the widest
   child's min-content width. The desktop rule already used `minmax(0, 1fr)`; the
   mobile override lost that protection. Use `minmax(0, 1fr)`.
4. `.editor-actions` -- four buttons in a flex row, no wrap -> 74px at 320px.
   Added `flex-wrap: wrap`.

Lesson: `overflow: hidden` on html/body hides responsive bugs from automated
checks. Audit with overflow visible, or measure `scrollWidth - clientWidth`.

## Keeping the preview link alive
The runtime kills child processes on recycle (container uptime resets to ~0 and
`/tmp` is wiped), which takes the server and the preview link down with it.
`scripts/keep-alive.sh` polls `http://127.0.0.1:$PORT/` every 15s and restarts
`app.main` when it fails, so the link recovers on its own. Start it with:

    setsid nohup ./scripts/keep-alive.sh > /dev/null 2>&1 < /dev/null &

Logs: `/tmp/rexeniot_live.log` (server), `/tmp/rexeniot_watchdog.log` (loop).
The watchdog does NOT survive a container restart itself -- it must be
relaunched after a recycle. If the link 502s, check `cat /proc/uptime` first: a
small value means the container restarted and the watchdog needs starting again.

Gotcha: invoking the script by relative path with `cd "$(dirname "$0")"` lands in
`scripts/`, not the repo root, and the interpreter path breaks. Resolve with
`readlink -f` and go up one level.

## Rebrand to "Sister RexenIOT"
Every `rexen` token became `rexeniot`, preserving case: `REXEN_*` env vars ->

double-applies into `rexeniotiot`.

- A blind case-insensitive sed over prose mangles display casing ("Sister

- grep's `--exclude=<name>` matches basenames, so `--exclude=rexen.log` silently
  does nothing when the path is `./data/rexen.log`. Filter the output instead.

## Launchers: why there are two .cmd files
`start.cmd` and `start-portable.cmd` (plus `.sh` twins) are NOT duplicates:
- `start.cmd` -- normal install. Uses a `.venv` next to the code and the system
  Python (`py -3` / `python`). State goes to `data/`. Requires Python preinstalled.
- `start-portable.cmd` -- self-contained. Creates `runtime/python` (downloads a
  standalone Python, ~30 MB) + `runtime/venv`, and redirects every cache into the
  folder via `REXENIOT_HOME`, `REXENIOT_PORTABLE=1`, `HF_HOME`, `XDG_CACHE_HOME`,
  `PIP_CACHE_DIR`. Intended to run from a USB stick. Also honours
  `REXENIOT_OFFLINE=1`. It falls back to a system Python if the download fails.

So the pair is "installed" vs "portable", and `.cmd`/`.sh` is Windows vs Unix.

## Watchdog bug: duplicate servers fighting over the port (fixed)
Symptom: preview link dead, `address already in use` in the log, 2-3 `app.main`
processes alive. Cause: the OLD `scripts/keep-alive.sh` decided liveness purely by
`curl --max-time 5`. Startup is slow -- TTS warm-up pulls ~107 HF files and starves
the event loop, so HTTP is unresponsive for 30-60s. The check read that as "dead",
spawned another server, which died on the bound port, forever.
Fix (rewritten `scripts/keep-alive.sh`):
- the server PID file (`/tmp/rexeniot_server.pid`) is authoritative, not the health
  check; a health failure alone never restarts
- `STARTUP_GRACE=120s` during which health failures are ignored
- `FAIL_LIMIT=6` consecutive failures (~90s) before a genuine restart
- `flock` on `/tmp/rexeniot_watchdog.lock` so only one watchdog can run
- won't start a server while something still holds the port
Verified: exactly 1 server process across the whole warm-up, HTTP 200 within 10s.

## Startup timing gotcha
`app/main.py` warms TTS in a background task, but the download starves the loop, so
`GET /` can be slow for the first ~60s on a cold cache. Do not diagnose "site is
down" from a single fast curl right after a start -- check the PID and the log first.
Also: the boot overlay is dismissed by adding the class `done` to `#boot`
(CSS `opacity:0; visibility:hidden`), NOT by setting `hidden` or `display:none`.
A Playwright check for `hidden`/`display` will falsely report "boot never clears".

## Test-methodology lessons (important, cost real time)
1. `scrollWidth` cannot detect overflow when an ancestor is `overflow: hidden`.
   Must measure each element's `getBoundingClientRect().right` against
   `window.innerWidth` instead.
2. `.messages` has `scroll-behavior: smooth`, so setting `scrollTop` and reading it
   back immediately returns the pre-animation value -> false "cannot scroll".
   Drive a real gesture (`mouse.wheel`) and wait, or the result is meaningless.
3. An empty message pane is not scrollable by definition; inject 30 messages before
   asserting scrollability or every device "fails".
4. On the chat HUD the DOCUMENT must NOT scroll (app-shell); the inner
   `.messages` pane must. On `/admin` the window MUST scroll (long form).
   They have opposite contracts -- test them separately.

## PORTABLE LAUNCHER BUG FOUND + FIXED (start-portable.cmd)
Root cause: ALL .cmd files had LF-only line endings (0 CRLF). cmd.exe mis-parses
LF-only batch: goto/label, parenthesised blocks and for-loops break, usually
SILENTLY. start-portable.cmd has 3 gotos + 1 label + deeply nested blocks, so it
was the one that visibly failed. start.cmd has 0 gotos so it mostly survived --
do not assume it was fine, it had the same latent defect.
FIX: converted both .cmd to CRLF (start.cmd 214, start-portable.cmd 200 CRLF).
Added .gitattributes pinning *.cmd=crlf, *.sh=lf, binaries binary -- so a future
git checkout / CI on Linux cannot silently re-break them.
Build script now RE-ASSERTS CRLF on .cmd when writing the zip (git on Linux would
otherwise ship LF again). Verified in the served download.

### Second real bug in start-portable.cmd
`set "TMP=%RUNTIME%\%TARBALL%"` clobbered Windows' built-in TMP (temp dir). That
breaks tar, pip and anything else needing a temp path. Renamed to PYTAR.
Also removed a caret line-continuation across the PowerShell call -- the line had
a TRAILING SPACE after `^`, which silently breaks the continuation in cmd.exe.
Same TMP rename applied to start-portable.sh for consistency (harmless there;

## Wake mode rework (web/js/app.js) -- user request

USER ASK: wake button stays ENABLED until the user turns it off; wake word needed
once per active interaction; after the idle timer (session_idle_s) the wake word
is needed again; avoid a mic enable/restart loop.

### BUG FOUND (pre-existing, real, would have bitten the user)
`pauseWakeForSpeech()` was called from speak() for ANY non-off wake mode, and it
STOPPED recognition. While ASLEEP (only waiting for a wake word) that pause is
pointless -- her own announcement cannot trigger a wake word. Worse, it made the
mic depend on `resumeWakeAfterSpeech()` running, which is only called from
audio.onended/onerror/the catch. So any missed completion (blocked autoplay, a
failed clip) left the mic STOPPED while the badge still read
"LISTENING FOR WAKE WORD" -- wake mode silently dead.
FIX: pause only when WAKE.mode === "awake". While asleep the mic keeps running.
This is what makes "stays listening until you switch it off" actually true.

### OTHER CHANGES
- Removed the auto-disarm: `onend` used to call setWakeMode("off") past 40
  restarts, contradicting "enabled until the user turns it off". Now it never
  self-disarms; it backs off instead (120ms, then 1000ms when restarts > 3).
- Single-flight restarts: `restartWakeIn()` + `WAKE.restartTimer` + `WAKE.starting`
  so an `onend` burst cannot stack start() calls into a mic on/off loop.
- Backoff counter is reset ONLY in onend, and only when the session actually
  lasted > 2000ms. Do NOT reset it in onstart/onaudiostart -- those fire for
  sessions that drop instantly and would cancel the backoff and restore the loop.
- `onend` returns early when `WAKE.resumeAfterSpeech` is set, so a playback pause
  is not undone by a restart mid-speech (she would hear herself).
- Watchdog (startWakeWatchdog, 2s) recovers ONE detectable state: a start() whose
  onstart never arrives, leaving WAKE.starting stuck true so every later restart
  is refused. It does NOT try to detect a mic that died without onend -- that is
  indistinguishable from a healthy silent session, so it is deliberately left
  alone rather than risk fighting a working mic.
- disarmWakeMode clears resumeAfterSpeech + stops the watchdog.
- loadPublicConfig now disarms if the admin turns wake_enabled off while armed.
- Toast wording: "Wake mode on. It stays listening until you switch it off."
