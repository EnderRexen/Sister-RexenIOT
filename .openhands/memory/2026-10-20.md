# 2026-10-20

## Reverted two "bug fixes" that were not bugs, and fixed a real one

Reported two bugs to the user with confident specifics. Both were wrong. The
checking that disproved them cost two commands.

### False bug 1 - "shipped config points at a model the default install cannot load"

`data/config.json` is in `.gitignore`, so it is never shipped. Fresh installs
generate it from the Pydantic defaults in `app/config.py`, and `TTSConfig()`
yields `model_id=KittenML/kitten-tts-mini-0.8` (the ONNX tier the light install
handles). The `kitten-tts-2` value I saw is *this sandbox's* runtime state.

Lesson: `data/` is runtime state, not product default. Check `git ls-files`
before calling anything a shipped default.

### False bug 2 - "tts.device=auto churns the watchdog on GPU-less machines"

Two errors. `auto` resolves to `(None, None)` here, so it never asks for cuda and
the fallback path never fires. And `scripts/keep-alive.sh` records zero restarts:
it is PID-authoritative with a 120s startup grace, written specifically to
survive TTS warm-up. I described a failure the code already defends against.

Worse, my earlier "fix" (commit d34d62d: probe CUDA in `auto` and pass it
explicitly) was unnecessary. kittenml's ONNX loader forwards `backend=None` as
`providers=[]`, and onnxruntime reads an empty list as "all available providers
in default precedence" - so onnxruntime-gpu already reaches CUDA. The torch
loader likewise picks cuda itself when device is None. Reverted the code, the
README table and the limitations note; rewrote `scripts/test_tts_device.py` to
pin the defer-to-library contract so nobody "fixes" it again.

Unverified and flagged as such: the `providers=[]` reading is from onnxruntime's
source, not measured - this box exposes no CUDA provider, so I could not
distinguish `providers=[]` from `["CUDAExecutionProvider"]` by experiment.

### Real bug - /api/admin/hardware/apply persisted tiers it could not load

`app/routers/admin.py` called `config.update(patch)` first, then
`engine.ensure_loaded()` inside a `try/except` that only logged. A failed
download or missing runtime was written to config permanently, so every later
start retried a model that cannot load, with only a log line as evidence. Very
likely how this sandbox ended up with `model_id=kitten-tts-2` against `tier=mini`.

Fix: load first, persist only on success; on failure return
`{"applied": {}, "error": ...}` and leave config alone. Also fixed
`web/js/admin.js`, which treated any 200 as success and would have reported a
failed apply as applied.

`scripts/test_apply_rollback.py` (7 assertions). Proved it is not vacuous by
re-introducing the old ordering: 5 of 7 go red, including
`model_id=KittenML/kitten-tts-does-not-exist` landing in config.

## Audit: does the frontend actually drive the backend?

User asked to confirm the wiring matches how the vendor requests it be
programmed. Built three tests rather than eyeballing it.

### Wiring is sound
- `scripts/test_config_contract.py` resolves all 50 frontend `data-cfg` keys
  against the real `AppConfig` schema, and every `<select>` option against its
  field's `Literal`. All resolve; no silent drops, no invalid option values.
- Voice selection genuinely works: 5 voices -> 5 distinct WAVs, and speed scales
  duration correctly (0.8 -> 4.04s, 1.0 -> 3.17s, 1.25 -> 2.49s).
- All 10 personalities reference valid voices. I suspected Kiki was invalid; it
  is a real vendor alias. Wrong again, cheaply this time.

### Vendor conformance (the actual question)
- `BASE_VOICES` matches `onnx_model.py:78` exactly.
- The HF repo's `config.json` ships `voice_aliases` mapping our friendly names to
  `expr-voice-N-m/f`; `_prepare_inputs` resolves them before validating, so
  friendly names are the vendor's supported path, not something we invented.
- `generate(text, voice, speed)` matches the vendor signature. Note the vendor
  default is `expr-voice-5-m` (not a friendly name), so a bogus voice would raise
  rather than default silently; our engine pre-validates against `self._voices`.
- TTS output verified end-to-end by round-tripping through faster-whisper:
  synthesized 7.51s of audio, transcribed back correctly including "21 degrees".
  That is real evidence of intelligibility, not just non-empty bytes.

### Real bug found (same class as last session, sibling endpoint)
`PUT /api/admin/config` persisted `tts.model_id` before loading it and only
logged failure -- identical to the `/hardware/apply` bug fixed last session.
Confirmed live: a bogus model_id landed in config permanently.

Fixed to load-before-persist, returning 400 that names the model. New
`test_config_tts_rollback.py` (7 checks, 5 go red against the old order) and
`test_config_ui_error.py` (operator sees the reason, not a generic failure).

Also: my first edit to admin.py was broken (orphan `try:`, duplicated comment).
`py_compile` caught it. Always compile after a scripted replace.

### Environment gotcha
`dev-stack.sh` is idempotent and will not restart a running app, so the live
server kept serving stale code and the fix looked ineffective. Had to kill the
`app.main` PID. Check `ps -eo pid,etime,cmd` for process age before believing a
live test.

### Not addressed
