## Reverted two "bug fixes" that were not bugs, and fixed a real one

Reported two bugs to the user with confident specifics. Both were wrong. The
checking that disproved them cost two commands.

### False bug 1 - "shipped config points at a model the default install cannot load"

`data/config.json` is in `.gitignore`, so it is never shipped. Fresh installs
generate it from the Pydantic defaults in `app/config.py`, and `TTSConfig()`
yields `model_id=KittenML/kitten-tts-mini-0.8` (the ONNX tier the light install
handles). The `kitten-tts-2` value I saw is *this sandbox's* runtime state.

Lesson: `data/` is runtime state, not product default. Check `git ls-files`
before calling anything a shipped default.

### False bug 2 - "tts.device=auto churns the watchdog on GPU-less machines"

Two errors. `auto` resolves to `(None, None)` here, so it never asks for cuda and
the fallback path never fires. And `scripts/keep-alive.sh` records zero restarts:
it is PID-authoritative with a 120s startup grace, written specifically to
survive TTS warm-up. I described a failure the code already defends against.

Worse, my earlier "fix" (commit d34d62d: probe CUDA in `auto` and pass it
explicitly) was unnecessary. kittenml's ONNX loader forwards `backend=None` as
`providers=[]`, and onnxruntime reads an empty list as "all available providers
in default precedence" - so onnxruntime-gpu already reaches CUDA. The torch
loader likewise picks cuda itself when device is None. Reverted the code, the
README table and the limitations note; rewrote `scripts/test_tts_device.py` to
pin the defer-to-library contract so nobody "fixes" it again.

Unverified and flagged as such: the `providers=[]` reading is from onnxruntime's
source, not measured - this box exposes no CUDA provider, so I could not
distinguish `providers=[]` from `["CUDAExecutionProvider"]` by experiment.

### Real bug - /api/admin/hardware/apply persisted tiers it could not load

`app/routers/admin.py` called `config.update(patch)` first, then
`engine.ensure_loaded()` inside a `try/except` that only logged. A failed
download or missing runtime was written to config permanently, so every later
start retried a model that cannot load, with only a log line as evidence. Very
likely how this sandbox ended up with `model_id=kitten-tts-2` against `tier=mini`.

Fix: load first, persist only on success; on failure return
`{"applied": {}, "error": ...}` and leave config alone. Also fixed
`web/js/admin.js`, which treated any 200 as success and would have reported a
failed apply as applied.

`scripts/test_apply_rollback.py` (7 assertions). Proved it is not vacuous by
re-introducing the old ordering: 5 of 7 go red, including
`model_id=KittenML/kitten-tts-does-not-exist` landing in config.

### Also

- Corrected this sandbox's config to a self-consistent mini/ONNX state and

## Hardware verification step (commit 9c90de9)

Built `hardware.plan()` + `/hardware/plan` (read) + `/hardware/plan/run` (apply,
verify-first by default). UI: "Verify & apply" card in the admin Hardware tab.

Three real bugs found while building, all worth remembering:

1. **espeak check was wrong.** `runtimes["espeak"]` only did `shutil.which()`.
   This box has NO espeak binary on PATH but TTS works fine, because the
   `espeakng_loader` wheel ships its own copy and is a hard dep in
   `app/main.py:126`. Checking PATH alone reported a working install as
   "action needed". Fixed: `phonemiser = espeak or espeakng_loader`, with a
   legacy fallback so an old cached profile is not read as a fault.

2. **Contradictory hint on a GPU-less box.** `/accelerator` advised
   `nvidia-smi  # confirm the driver sees the GPU` when `torch_info.cuda_version`
   was set -- but this box has torch 2.14.1+cu130 and *no GPU at all*, so it told
   the user to check a driver that isn't there. Fixed: the whole hints block now
   returns [] when `not profile.get("gpu")`. A CUDA build with no GPU is normal
   for a container; it is not a driver problem.

3. **No-op device change broke the default profile.** `_pick_device` returns
   `"cpu"` when no GPU is present, but `"auto"` already means CPU there. Proposing
   that flip changed the config, which dropped the shipped `balanced` profile out
   of "in use" (it pins `device: "auto"`) and made `test_profiles_ui` fail with 3
   errors. Rule now: only propose a device when it changes behaviour -- keep
   `cpu` if already `cpu`, else settle on `auto`. Caught by running the existing
   profiles UI suite, not by my new tests.

**Stale-cache trap (bit me twice).** `data/hardware.json` is cached and
`/accelerator` reads keys off it. Adding a probe without invalidating the cache
makes the reader see a missing key and report a *false finding* (first
`device`/`devices`, then `phonemiser`). Added `hardware.PROFILE_VERSION`, now 3;
`cached()` returns None on mismatch so callers rescan. If you add a probe to
`_accelerators()`/`_runtimes()`, bump `PROFILE_VERSION`.

Other facts:
- `PUT /api/admin/config` body is `{"patch": {...}}` -- a bare nested object 422s.
  `POST /hardware/plan/run` body is `{"verify": true}`.
- `config.LLMConfig.provider` Literal is `auto|openai|anthropic|ollama|offline`;
  there is no `openai_compatible`. `hardware_apply` uses `"ollama"`.
- This box: torch CUDA 13.0 build, `cuda.is_available()` False, no /dev/nvidia*,
  ORT providers = Azure+CPU, `ort.get_device()` = "CPU". Good fixture for the
  "CUDA build, unreachable GPU" path.
- `scripts/test_attach_ui.py` FAILS on a clean tree (needs `/tmp/uptest/usage.csv`
  and the local model to echo file contents). Pre-existing, unrelated -- verified
  by stashing my changes and reproducing.
- Tests need `PYTHONPATH=.` for `import app`.

## Model prerequisites + in-use state (commit 3dc0d07)

Three defects in the admin Hardware tab, all found by reading what the UI actually
consumes instead of trusting the endpoint to be complete.

1. **`/admin/models` served `ALL_MODELS` raw.** It has no `fits` / `blockers` /
   `requirements` / `downloaded`, but `renderModels()` renders from exactly those,
   so *every* Download button was `disabled` and no "downloaded" badge ever
   appeared. `list_models` now merges `hardware.recommend(profile)["models"]`
   keyed by repo via `_catalog_view()`. Lesson: the model list is rendered from
   **two** endpoints -- `recommendations.models` from the scan and `catalog` from
   `/models`. Annotate both or a badge appears on one path only. That is why
   `_with_model_state()` exists and is applied in `/hardware` and `/hardware/scan`.

2. **`requires.torch` was advertised and never acted on.** The 1.7B tier
   downloaded its weights, then the load failed at import with nothing in the UI
   to fix it. `model_catalog.prerequisites(entry)` now reports the requirement set,
   whether it resolves, what is missing, and the command. The row offers "Install
   PyTorch stack" instead of a dead-end Download; `/models/load` refuses with a
   clear 409 naming the missing piece.

   Install safety: the endpoint takes a **set key**, never a package name
   (`InstallRequest.set`), so it can only run pip against `requirements-full.txt`
   / `requirements-gpu.txt`, which ship with the app. Arbitrary strings are
   rejected 400 -- verified with `requests`, `../etc/passwd`, `full; rm -rf /`.
   Installs are serialised with `asyncio.Lock` (concurrent pip runs corrupt each
   other's metadata) and **post-checked by import**, because pip can exit 0 while
   an import still fails.

3. **The Use button had no active state.** Now: `active` on the catalog entry
   (`_active_tts_repo()` = engine status, falling back to config), an "in use"
   badge, a green `.btn-ghost.is-active`, and `.model-row.in-use` (which must force
   `opacity: 1`, else the active row inherits `.unfit`'s 0.62 and reads as a
   problem). `useTtsModel` calls `refreshModels()` so the mark moves immediately.

### Recurring bug class: a probe that cannot see the difference
`onnxruntime` and `onnxruntime-gpu` **share an import name**, so `find_spec`
reported the GPU set as *satisfied* while only the CPU build was installed --
another false "ready". `missing_for("gpu")` now checks
`"CUDAExecutionProvider" in ort.get_available_providers()`. Same shape as the
phonemiser bug (probed `PATH`, missed the bundled wheel) and the stale profile
cache (missing key looked like a real finding): **an import or presence check is
not evidence the capability works.**
