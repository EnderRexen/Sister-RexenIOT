# RexenIOT -- Nix packaging port (2026-09-17)

Sister RexenIOT (project `1e98be29881e4f70b4a57c8f52f438fd`, branch `main`) had a
runtime-pip bootstrap and five overlapping requirements files. Ported it to
`pyproject.toml` + `uv.lock` + a uv2nix flake, keeping `scripts/bootstrap.py`
untouched as the portable path.

## Gotchas that cost real effort

- **tree-sitter-nix mis-parses a path literal immediately followed by a comma.**
  `src ? ./..,` produces `MISSING identifier` at the *next* line's column, which
  points nowhere near the cause. Jarvis's `nix/package.nix` dodges this by
  writing `, src ? ./..` (comma first). Keep path defaults last, or lead the
  comma. Verified by bisection: `{ src ? ./.., }: src` fails, `{ src ? ./.. }: src`
  passes. Note the token reported by the grammar is not the offending token.
- **uv `[tool.uv] dependency-metadata` is the declarative form of
  `pip install --no-deps`.** `kittenml==0.9.4` hard-declares torch, torchaudio,
  transformers and 15 others, but the ONNX backend needs none of them. An entry
  `{ name = "kittenml", version = "0.9.4", requires-dist = [] }` strips them and
  the lock records kittenml with no `dependencies` array. This is what keeps the
  light tier from pulling 2.5 GB of PyTorch.
- **`uv2nix`'s default branch is `master`, not `main`** -- `raw.githubusercontent`
  / `.../main/...` 404s, and the API tree call returns `Not Found`.
- **`mkPyprojectOverlay` defaults to `deps.all`**, and its own source comment warns
  that resolving the entire workspace "will not work for resolutions with
  conflicts". RexenIOT declares a `gpu`/`directml` conflict (both provide the
  `onnxruntime` module), so the overlay must pass an explicit `dependencies`.
- `workspace.deps` shape: `default` = no extras (light tier), `optionals` = all
  extras, `groups` = all dev-groups, `all` = everything. `mkVirtualEnv` takes a
  deps attrset, e.g. `{ rexeniot = [ "stt" "full" ]; }`.

## RexenIOT specifics

- `app/config.py:23` resolves `ROOT` from `$REXENIOT_HOME`, else the source tree;
  `WEB_DIR = ROOT/web`, `DATA_DIR = ROOT/data`. That env var is the integration
  point: in the store ROOT is read-only, so `nix/package.nix` points
  `REXENIOT_HOME` at a writable state dir and symlinks the packaged `web/` into
  it, re-linking on every start so a rebuild cannot leave a dangling store path.
- Entry point is `app.main:main`; it takes `--host/--port/--no-browser`.
- The app package has subpackages (`app/llm`, `app/routers`, `app/tools`,
  `app/tts`, `app/stt`), so setuptools needs
  `[tool.setuptools.packages.find] include = ["app*"]` -- a flat
  `packages = ["app"]` silently omits them.
- Installed versions in the working venv (Python 3.13.15): fastapi 0.143.2,
  uvicorn 0.54.0, pydantic 2.14.1, numpy 2.5.4, onnxruntime 1.31.0,
  huggingface_hub 1.33.0, faster-whisper 1.2.1, av 19.0.2, psutil 7.2.2,
  paho-mqtt 2.1.0, kittenml 0.9.4.
- `.gitignore` needs `result`/`result-*`/`.direnv/` for the flake builds.

## nixpkgs `src` collision (2026-09-17) -- bit the first real build

`callPackage ./nix/package.nix { }` failed with
`error: The "src" package has been renamed to "simple-revision-control"`.

Cause: nixpkgs added a **throwing top-level alias** `src` (aliases.nix line
2557, added 2025-11-19). `callPackage` auto-injects top-level attributes for any
formal the caller does not supply, so a formal named `src` receives the throwing
alias and the `? ./..` default is never consulted. The error text says
"falsely constructed overlay", which sends you looking in the wrong place.

Fix: name it `srcDir` (exists nowhere in nixpkgs) and write `src = srcDir;`.
General rule for this repo: **never name a `callPackage` formal after a nixpkgs
top-level attribute** -- `src` is the one that bites, but the class of bug is
"formal name collides with the package set". Jarvis's `package.nix` avoids it
only because it predates the 2025-11-19 alias.

Also added a `cleanSourceWith` filter dropping `.git`, `.venv`, `data`,
`.direnv`, `__pycache__`, `result` -- the repo carries a large `.venv` and a
runtime `data/` that should not be copied into the store.

Confirmed by the same run: the flake **evaluated**, `flake.lock` was generated,
and uv2nix resolved the overlay -- so the `mkVirtualEnv` / `mkPyprojectOverlay`
call shapes in `flake.nix` are correct. Only the parameter naming was wrong.

## nixpkgs attribute-name traps (2026-09-17)

Two bugs from the same class: a `callPackage` formal named after something that
is not the nixpkgs attribute you want.

1. `src` -- top-level **throwing alias** (aliases.nix, added 2025-11-19).
   `callPackage` injects it and the `? ./..` default is never reached. Fixed by
   renaming to `srcDir`. The error text ("falsely constructed overlay") misleads.
2. `espeak-ng` -- **not a top-level attribute**. all-packages.nix has
   `espeak = espeak-ng;`; `espeak-ng` is only a let-bound name. A formal spelled
   `espeak-ng` fails with "called without required argument". Use `espeak`.

Rule: before naming a formal, grep all-packages.nix for `^  <name> = ` and
aliases.nix for `^\s*<name>\s*=\s*throw`. Cheap, catches both classes.

## Runtime gaps the wrapper had (2026-09-17)

- `app/hardware.py` probes `shutil.which("espeak-ng")` / `which("espeak")` and
  falls back to the `espeakng_loader` wheel. The wheel is a declared dep, so the
  app worked, but the wrapper put only `coreutils` on PATH and the panel then
  told the operator to `apt install espeak-ng`. Now `espeak` is on PATH.
- `app/config.py` ROOT = `$REXENIOT_HOME` or the source tree; `main.py` calls
  `ensure_dirs()`. `data/` is pure runtime state -- personalities, skills and
  voice profiles all have `BUILTIN` defaults in code -- so excluding it from the
  derivation source is correct.
- The admin panel shells out to `python -m pip install -r requirements-*.txt`
  (app/routers/admin.py). Those files are repo-root relative and not packaged,
  so in-app dependency installs cannot work in a Nix install. Expected: manage
  tiers via `services.rexeniot.tier` instead. Not "fixed" -- it is a genuine
  design mismatch worth telling the user about.

## Delivering files to the user (2026-09-17) -- what actually works

The user's machine and this sandbox share no filesystem. Two delivery routes
failed before one worked:

1. `git push` -- **impossible**. `EnderRexen/Sister-RexenIOT` is private and the
   token has **0 GitHub App installations** (`GET /user/installations` ->
   `total_count: 0`). The token is valid (`torvalds/linux` -> 200) and
   authenticated as `EnderRexen`, but sees none of the user's private repos.
   `OH_GIT_CREDENTIAL_ACCESS_TOKEN_GITHUB` is a JWT with
   `aud: openhands:secret-lookup` -- an internal secret-lookup token, not a git
   credential. No credential helper is configured.
2. `python -m http.server` + `curl` from the work host -- **fragile**. The
   background server does NOT survive between agent turns, so the URL silently
   404s. Worse, `curl ... ; tar ...` (semicolon) let `tar` extract the *stale*
   tarball still on disk, so the user rebuilt the old file and hit the identical
   error -- provable because the Nix store hash was byte-identical
   (`iizipc71rh7pjklsscn943va45dcaahl-source`) and the trace pointed at the old
   line number.
3. **`cat > file <<'EOF' ... EOF` heredoc pasted into chat + `sha256sum` check
   -- this worked.** No server, no network, no process lifetime to worry about.
   Prefer it whenever the user has a shell. Always give the sha256 so they can
   confirm the paste survived intact, and do NOT put inline `#` comments on the
   verification lines -- they get passed as extra filename arguments and produce
   confusing errors.

If a download route is used anyway: `rm -f` the target first, `curl -fL
--retry 3`, chain with `&&` not `;`, and `sha256sum -c` before extracting.
