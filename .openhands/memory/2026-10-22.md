## Local dictation (faster-whisper), enabled by default — commit 3cc2283

Shipped server-side speech-to-text. The browser records a clip with MediaRecorder
and POSTs it to `/api/transcribe`; the server decodes and transcribes locally.
This replaced the browser-only path, so dictation no longer needs Chrome/Edge and
the audio never goes to the vendor.

Decisions and the reasons, since these were expensive to establish:

- **Decode with PyAV ourselves; do not hand faster-whisper a file.** PyAV 19.0.2
  rejects the `metadata_errors` kwarg faster-whisper passes internally, so its own
  file path raises. Decoding to mono 16 kHz float32 and passing the ndarray works
  and is a smaller surface. WAV and Opus-in-WebM (what MediaRecorder emits) both
  decode correctly — libsndfile cannot read the WebM container, so a WAV-only
  decoder would have passed a naive test and failed in the field.
- **Enabled by default is a packaging decision, not just a config default.** A
  feature that is on by default but silently missing its engine is worse than one
  that is off. So `scripts/bootstrap.py` installs the set (~100 MB real add;
  onnxruntime + huggingface_hub are already in the base set) on a normal run, with
  a `--stt` flag defaulting on and `REXENIOT_NO_STT=1` to skip. It uses its own
  marker `.venv/.req-hash.stt` so a base-req change does not force an STT reinstall.
- **Phase B proves it with `--prepare-stt`**, which speaks a known line and
  transcribes it back. A load is not proof. Failure is a warning, not fatal.
- **`voice_input.engine` "auto" prefers the server**, as the config docs and admin
  UI already claimed. The first cut made "auto" prefer the browser whenever a
  native recogniser existed — the opposite of the documented behaviour. "auto" and
  "server" now differ only when the set is missing: "auto" falls back to the
  browser, "server" tells the user what to install.

Test notes worth keeping:

- The existing `scripts/test_*.py` UI tests hardcode `127.0.0.1:8060`. When the
  suite reports failures, check whether the test just needs a live server: passing
  the live port (`python scripts/test_osk.py http://127.0.0.1:12000`) turns 6 of 7
  "failures" green. `test_attach_ui.py` additionally needs a `/tmp/uptest/usage.csv`
  fixture. Neither is a regression.
- `scripts/test_model_prerequisites.py` has a hardcoded allow-list of requirement
  set keys; adding a set means adding its key there.
- `web/js/app.js` is an ES module, so its scope is unreachable from `page.evaluate`.
  Added `window.__rexeniot = { state, useLocalCapture, ... }` so a browser test can
  reach it. This is what makes `scripts/test_stt_ui.py` possible.
- For a browser mic test, Chromium's `--use-file-for-fake-audio-capture=<wav>` plus
  `--use-fake-ui-for-media-stream` gives a synthetic microphone. Generate the WAV
  with the app's own TTS engine so the phrase is known.


## Launcher consolidation + admin CSS fix (later the same day)

**Launchers: four -> two.** Deleted `start-portable.cmd`/`.sh`; `start.cmd`/`start.sh`
are now the portable ones. `--portable` removed from `scripts/bootstrap.py` (the
portable path became unconditional), so its `--help` no longer lists it.

**Measured proof, not eyeballing.** To show the admin CSS bug was real and then
fixed, drive Chromium via Playwright and compare `getBoundingClientRect()` of each
control against its row siblings, in the same page, with and without the fix
(`page.add_style_tag` re-injects the old rule). "API key (env var preferred)" had
its input **21px** below its row-mates; after the fix, 1px (sub-pixel rounding).
`/usr/bin/chromium` + `--no-sandbox` works, no `playwright install` needed.

**The CSS root cause.** `.field-grid label { display:flex; flex-direction:column }`
makes *every* child a flex item - including an inline `<span>` hint. So
`API key <span class="muted">(env var preferred)</span>` became three stacked rows
and the input dropped. Fix: label `display:block`, control spaced with
`margin-top:6px`; keep `label.checkbox` a flex row. One rule fixes all nine
affected labels (find them with a regex over `<label>...</label>` containing both a
`<span>` and an `<input|select>` - a plain `grep -n '<label><span'` finds only the
ones on one line, i.e. 4 of 9, which is how the count was first under-reported).

**Verify a "regression" against HEAD before blaming your change.** `test_profiles_ui.py`
reports `3 FAILED` (preselected profile, "in use" badge, option-list marking).
`git checkout HEAD -- web/css/admin.css web/admin.html` and it fails identically -
pre-existing, unrelated. Cheap and decisive; do it before investigating.

**Stale comments are a real hazard here.** After the rename, four docstrings still
described "the portable pair" in the present tense, implying files that no longer
exist. Reworded to the past tense so the historical *why* survives without
implying current structure.

**Still-open findings (told the user, not fixed):** in `_inject_prompt`
(`app/tools/comfyui.py`) the comment says an empty/placeholder text is the positive
slot, but the branch routes an empty-text `CLIPTextEncode` node to the *negative*
slot - the comment and code disagree. Also the LLM catalog entries are Ollama tags
that `/admin/models/download` deliberately refuses, returning an `ollama pull`
command instead - worth confirming that stays intended.

## NixOS: yes, but not with `./start.sh` directly (verified by ELF inspection)

The blocker is the **manylinux wheels**, not Python. Inspected every native `.so`
in `.venv` by reading the ELF headers directly (no `patchelf`/`readelf` on this
box; parse `PT_INTERP`, `DT_NEEDED`, `DT_RUNPATH` with `struct`):

- `onnxruntime_pybind11_state*.so` -> `DT_NEEDED` includes **`ld-linux-x86-64.so.2`**
  plus `libstdc++.so.6`, `libgcc_s.so.1`, `libdl.so.2`, `librt.so.1`,
  `libpthread.so.0`, `libm.so.6`, `libc.so.6`; `DT_RUNPATH` is `$ORIGIN` only.
- `espeakng_loader/libespeak-ng.so` (dlopen'd, no PT_INTERP) -> `libstdc++.so.6`,
  `libm.so.6`, `libgcc_s.so.1`, `libc.so.6`, and a **baked-in RPATH pointing at the
  wheel-builder's CI dir** (`/home/runner/work/espeakng-loader/...`), which does not
  exist on any target machine. It works here only because glibc falls back to the
  default search path.
- Native modules in the web stack too: `pydantic_core`, `uvloop`,
  `watchfiles/_rust_notify.abi3.so`, `psutil/_psutil_linux.abi3.so`.

NixOS has no FHS `/lib64/ld-linux-x86-64.so.2` and no `/usr/lib`, so those
`dlopen`s fail with "cannot open shared object file". Also `python3 -m venv` /
`ensurepip` is unreliable there. **Fix: run inside an FHS env** (`buildFHSEnv` /
`steam-run`), which populates `/usr/lib` from `targetPkgs`. `nixpkgs` python +
`stdenv.cc.cc.lib` + `zlib` + `glibc` covers every `DT_NEEDED` above.

Which libs actually need supplying: in a bare CPython process `libc.so.6` and
`libm.so.6` are **already loaded** (reused by SONAME), but `libstdc++` and
`libgcc_s` are **not** - those two are what must come from outside. Check with
`/proc/self/maps`.

`kittenml` ONNX path imports espeak only lazily
(`kittentts_legacy/model.py` -> `onnx_model.py`), so a NixOS `espeak-ng` on PATH
can substitute for the bundled wheel.

## Plasma Desktop on NixOS: nothing desktop-specific breaks

Plasma changes nothing about the loader problem, and adds no new one. The app has
**no desktop integration at all** - no tray icon, no D-Bus, no `notify-send`, no
`.desktop`/`.service` files, no systemd unit. Verified by grep across `app/`.

- **Audio is played by the browser, not the server.** `app/tts/engine.py` only
  encodes WAV bytes (`sf.write`, `PCM_16`) and `/api/speak` returns `audio/wav`;
  `web/js/app.js` does `new Audio()` + `audio.play()`. There is **no**
  `sounddevice`/`pyaudio`/`alsa` dependency, so nothing server-side needs to reach
  a sound device. Consequently **the app works in a headless FHS sandbox**: the
  browser is the audio sink and it lives on the Plasma session, outside the sandbox.
- **Mic likewise**: `getUserMedia` + `MediaRecorder` in the browser, POSTed to
  `/api/transcribe`. PipeWire/PulseAudio access happens in the browser process.
- **Browser opening works under Plasma.** `app/main.py` calls
  `webbrowser.open("http://localhost:{port}/")`. Python's `register_X_browsers()`
  registers `xdg-open` first, and Plasma provides `xdg-open`, which honours
  `xdg-settings`/`BROWSER`. The explicit KDE branch needs `kfmclient` (old KDE4
  tooling) and will usually miss on modern Plasma - harmless, because `xdg-open`
  is the first entry anyway.
- **Wayland vs X11 is irrelevant here.** The app is a web server plus a browser
  tab; it has no X11/Wayland client code.
- **State paths**: the launcher exports `XDG_CACHE_HOME` *inside* the app folder
  (`start.sh` line 41), so the app never writes to Plasma's `~/.cache`. `HF_HOME`
  and `PIP_CACHE_DIR` are likewise folder-local.
- **The on-screen keyboard is for touch/kiosk**, not a Plasma desktop; it is
  optional and off unless enabled.
- `server.host` default is `127.0.0.1` (`app/config.py`), `port` default `8000` in
  the schema but the launchers pass `8060`. Note `open_browser` is read from config
  only - there is **no env override** for it, so a headless start needs
  `--no-browser` (which is what `scripts/keep-alive.sh` passes).

The one genuinely Plasma-specific thing worth doing is a user systemd unit so the
server starts with the session; the repo ships none.
